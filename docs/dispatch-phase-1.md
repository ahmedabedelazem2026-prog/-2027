# توزيع الرحلات - المرحلة الأولى

## ما يعمل في الكود
- عند إنشاء الرحلة، يبحث الخادم عن السائقين المعتمدين والمتصلين داخل نفس `cityId`.
- يفحص آخر موقع محفوظ في `drivers/{driverId}.location` بالشكل `{ latitude, longitude }`.
- يرتب المرشحين حسب المسافة التقريبية بخط مستقيم، ويرسل عرضًا لأول خمسة سائقين كحد أقصى.
- ينشئ العرض في `trips/{tripId}/offers/{driverId}` بحالة `pending`.
- تطبيق السائق يستطيع الاستماع إلى مستند العرض الخاص بمعرّف السائق فقط.
- القبول يتحقق من وجود العرض وحالته ومن اعتماد السائق واتصاله، ثم يستخدم Firestore transaction حتى يفوز سائق واحد فقط.

## المطلوب قبل التشغيل
1. تحديث موقع السائق بصورة موثوقة أثناء اتصاله؛ لا تعتمد على إحداثيات يرسلها العميل عند قبول الرحلة.
2. إعداد Firebase Authentication وApp Check للتطبيقات الثلاثة.
3. نشر قواعد Firestore والفهارس، ثم نشر Cloud Functions بعد ضبط المشروع والفوترة والحصص.
4. إضافة واجهة تستمع إلى `trips/{tripId}/offers/{uid}` وتعرض الطلب للسائق.
5. اختبار التزامن وقواعد الوصول في Firebase Emulator قبل إطلاق أي رحلات حقيقية.

## ما لم يُنفّذ بعد
هذه نسخة موجة أولى وليست نظام توزيع متدرج مكتملًا. لا توجد حتى الآن جدولة تلقائية لفتح موجات لاحقة أو إلغاء العروض المنتهية أو إرسال Push Notifications عبر FCM. كما أن ترتيب المسافة حاليًا تقريبي وليس زمن وصول عبر خرائط الطرق. يلزم عامل موثوق مثل Cloud Tasks/مجدول للموجات اللاحقة، مع إعداد تكلفة الخدمة قبل تفعيله.

## ملاحظات أمان
- إنشاء الرحلة والقبول وتعديل الحالة تتم من Cloud Functions باستخدام Admin SDK، وليس بكتابة مباشرة من تطبيق العميل.
- قراءة عروض السائق مقيدة بمستند UID الخاص به.
- لا تضع مفاتيح Firebase الخاصة أو مفاتيح Google المقيدة في المستودع؛ استخدم إعدادات البيئة والأسرار المناسبة.
